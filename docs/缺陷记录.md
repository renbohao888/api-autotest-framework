两个缺陷都是在框架 v1 版本上跑用例时暴露的，附复现命令、原始日志与修复后的回归结果。

## DEF-001 取消 / 支付超时关单后库存不回补，导致库存被「已关闭订单」永久占用

| 项 | 内容 |
| --- | --- |
| 严重级别 | 高（资损类：库存被占用，可售数量虚低） |
| 发现版本 | 框架 v1 + SUT v1 |
| 发现用例 | `ODR-004`（待支付→已取消）、`ODR-005`（支付超时关单）、`test_stock_restore_invariant` |
| 复现命令 | `python scripts/run.py`（或 `pytest testcases/test_30_order_state.py -k ODR-004`） |

**复现步骤**

```bash
curl -X POST localhost:8899/api/admin/reset -H "Content-Type: application/json" -d '{"stock":5}'
TOKEN=$(curl -s -X POST localhost:8899/api/auth/login -H "Content-Type: application/json" \
        -d '{"username":"tester","password":"test123"}' | python -c "import sys,json;print(json.load(sys.stdin)['data']['token'])")
NO=$(curl -s -X POST localhost:8899/api/seckill/order -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" -d '{"activityId":1}' | python -c "import sys,json;print(json.load(sys.stdin)['data']['orderNo'])")
curl -X POST localhost:8899/api/order/$NO/cancel -H "Authorization: Bearer $TOKEN"
curl -s localhost:8899/api/admin/stock/1     # 期望 stock=5，实际 stock=4
```

**期望**：取消 / 支付超时关单属于「释放库存」的终态，库存应回到 5，`remainStock=5`。
**实际**：库存停留在 4；订单状态已变为 `CANCELED` / `TIMEOUT_CLOSED`，但库存没有回补。

**失败日志（框架原始输出）**

```
E  AssertionError: [响应字段子集] POST /api/order/SO2026091221155256CEFF/cancel -> 200 (4.01ms)：
   以下字段不符合预期（data）：
       - remainStock 期望 5，实际 4
E  AssertionError: [数据库校验] 期望 8，实际 5
   （SQL：SELECT stock FROM activity WHERE activity_id=1，params=()）
```

**根因**：`service/store.py::change_state` 只做了「订单状态更新」，没有在进入
`CANCELED` / `TIMEOUT_CLOSED` 时把占用的库存还回去（缺少补偿逻辑）。

**修复**：在同一个 `BEGIN IMMEDIATE` 事务里，对 `RESTOCK_STATUSES` 的终态执行
`UPDATE activity SET stock = stock + 1, version = version + 1`，保证「状态变更 + 库存回补」原子生效。

**回归验证**：`ODR-004`、`ODR-005`、`test_stock_restore_invariant` 全部通过；
不变量「当前库存 + 有效订单数 = 初始库存」成立。

## DEF-002 同一用户并发下单时服务返回 500，未返回业务码 1009

| 项 | 内容 |
| --- | --- |
| 严重级别 | 高（并发下接口 5xx + 幂等语义失效：可能多单 / 多扣库存） |
| 发现版本 | 框架 v1 + SUT v1 |
| 发现用例 | `test_same_user_concurrent_orders_only_one_success`（同一 token 的 8 个并发会话） |
| 复现命令 | `pytest testcases/test_40_consistency.py -k same_user -v` |

**期望**：8 个并发请求中只成功 1 单，其余返回 1009（重复下单）或 1008（限流），无 5xx。
**实际**：`成功 1 ｜ 重复下单 0 ｜ 限流 5 ｜ 其它 [500]`，其中 2 个请求返回 HTTP 500。

**失败日志（框架原始输出）**

```
INFO  atf.case.concurrency | 单人并发结果：成功 1 ｜ 重复下单 0 ｜ 限流 5 ｜ 其它 [500]（0.03s）
E  AssertionError: [其余请求只能是「重复下单」或「限流」] 期望 8，实际 6
```

**根因**：两个问题叠加。

1. **TOCTOU 竞态**：重复下单校验（`SELECT order_no FROM orders WHERE activity_id=? AND user_id=?`）
   放在写事务之外，多个并发请求可以同时通过校验；
2. **异常未转换**：唯一索引 `uk_order_user` 在并发插入时抛 `sqlite3.IntegrityError`，
   而 `create_order` 直接向上抛，被应用的全局兜底 handler 当成未知异常返回 500。

**修复**：

1. 把重复下单校验挪进 `BEGIN IMMEDIATE` 写事务内，与「扣库存 + 落订单」串行化；
2. 显式捕获 `sqlite3.IntegrityError`，转换成业务码 `1009`（该走的业务分支要返回业务语义，而不是 500）；
3. 顺带把回滚封装成 `_safe_rollback`，避免「回滚失败掩盖真实异常」。

**回归验证**：修复后 `成功 1 ｜ 重复下单 2 ｜ 限流 5 ｜ 其它 []`，用例通过；
数据库侧校验库存只扣 1、库内只有 1 单；200 并发抢购用例同时保持绿灯。
